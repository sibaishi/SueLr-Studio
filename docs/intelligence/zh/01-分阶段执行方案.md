# 分阶段执行方案

## 总体执行原则

整个计划必须分阶段推进，不能一次性重写。

每个阶段都要保证：

- App 仍然可用
- 当前旧 Agent API 在切换前继续可用
- 第一实现和验收环境是 `desktop` 与 `local-web`
- `server-web`、多用户共享知识库、三端同步后置
- 先加新模块，再逐步替换旧模块
- 后端输入必须 Zod 校验
- 错误响应保持 `{ error, code, status }`
- 工作流执行继续走现有 `ExecutionService`
- 运行时文件继续走 storage resolver
- 中文文本保持 UTF-8
- 每个阶段都有明确验收标准

## 阶段 0：基线治理与文档落地

目标：

先把方向、门禁、现状和风险固定下来。

范围：

- 落地公开规划文档
- 修改 docs 门禁，允许 `docs/intelligence/`
- 明确旧 Agent 体系是 legacy
- 盘点当前 Agent、Memory、Tool、Workflow 执行代码
- 修复或登记中文乱码问题

不做：

- 不替换运行时
- 不改 UI 交互
- 不改模型调用

验收：

```bash
npm run check:docs
npm run check:encoding
```

## 阶段 1：本地 Intelligence Runtime 骨架

目标：

建立一个并行的新本地后端智能模块，不影响旧 Agent。

新增目录：

```text
backend/src/modules/intelligence/
  intelligence.routes.ts
  intelligence.controller.ts
  intelligence.schema.ts
  runtime/
  skills/
  knowledge/
  agents/
```

第一批只读 Skills：

```text
knowledge.search
workflow.list
workflow.inspect
model.list
```

第一批 API：

```text
POST /api/intelligence/runs
GET  /api/intelligence/runs/:id
GET  /api/intelligence/skills
GET  /api/intelligence/knowledge
```

验收：

- 新 API 可用
- 旧 `/api/agent` 不受影响
- run trace 可保存和读取
- 只读 Skills 不能产生副作用
- 不依赖 `server-web` 用户体系或同步能力

## 阶段 2：本地 Workflow Architect MVP

目标：

让 Agent 能在本地根据需求生成工作流草案，但不自动保存、不自动执行。

新增：

```text
workflow-builder/
  workflow-intent.schema.ts
  workflow-draft.schema.ts
  workflow-compiler.ts
  workflow-validator.ts
```

新增 Skills：

```text
brief.parse
workflow.plan
workflow.createDraft
workflow.validate
```

前端入口：

```text
src/domains/workflow/
  工作流 AI 助手
  草案预览
  应用草案确认
```

验收例子：

用户输入：

```text
帮我做一个商品图生成工作流，输入产品图和一句卖点，输出 6 张不同风格的电商主图。
```

系统输出：

```text
Image Input
Text Input
Prompt Helper / AI Chat
Image Gen x 6
Image Compare / Review
Save File
Output
```

要求：

- 用户能预览
- 用户确认后才能应用
- React Flow 状态仍由 React Flow 管

## 阶段 3：本地工作流执行闭环

目标：

用户确认后，智能系统能执行工作流、诊断失败、总结结果。

新增 Skills：

```text
workflow.execute
workflow.diagnose
workflow.suggestInputs
workflow.summarizeRun
```

规则：

- 执行必须走现有 `ExecutionService`
- 工作流目标必须来自当前请求或用户明确确认
- 输入覆盖必须来自当前请求或用户明确确认
- 知识库只能提供建议，不能静默执行

验收：

- 草案可保存并执行
- 执行失败能给出节点级诊断
- 执行成功能输出资产列表和运行报告
- 断开 SSE 不等于取消
- 显式取消仍走现有 cancel endpoint

## 阶段 4：本地 Studio Brain 知识库 MVP

目标：

把简单 Memory 升级成本地个人/项目细分类知识库。

第一版 JSON 文件：

```text
knowledge/user-memory.json
knowledge/project-knowledge.json
knowledge/brand-knowledge.json
knowledge/workflow-knowledge.json
knowledge/asset-knowledge.json
knowledge/run-knowledge.json
knowledge/prompt-library.json
knowledge/model-knowledge.json
```

新增 Skills：

```text
knowledge.search
knowledge.write
knowledge.linkAsset
knowledge.summarizeRun
knowledge.extractPreference
knowledge.promoteToTemplate
```

验收：

- 知识记录有类型、来源、作用域、证据
- 运行经验必须来自真实 run trace
- 品牌规则、项目规则写入前需要确认
- 旧 memory 可以迁移或导入
- 第一阶段不实现跨用户共享知识库和全局审核流

## 阶段 5：本地设计团队 MVP

目标：

在本地引入多角色团队，但先用可控的项目经理调度制。

新增：

```text
teams/team-orchestrator.ts
teams/team-template.service.ts
agents/role-runner.ts
planner/project-plan.service.ts
review/review.service.ts
```

第一批团队：

```text
品牌视觉团队
工作流工程团队
电商素材团队
```

协作模式：

```text
串行生产
并行提案
评审返工
```

验收：

- 项目经理能拆任务
- 创意总监能评审方向
- Workflow Architect 能出工作流草案
- 质检角色能打分
- 每个角色输出都有 trace

## 阶段 6：本地资产生产流水线扩展

目标：

把本地图片、视频、文案、提示词、资产包都纳入 Skills。

新增 Skills：

```text
prompt.optimize
prompt.variant
copy.write
image.generate
image.edit
image.compare
video.generate
asset.package
asset.index
```

规则：

- 图片/视频继续复用现有 provider 和输出路径
- 不把大 base64 写进日志或知识库
- 高成本生成默认需要确认

验收：

- 团队计划能调用生产 Skills
- 资产能在结果面板看到
- 资产能写入素材知识库

## 阶段 7：本地旧 Agent 默认切换

目标：

把本地聊天、设置、工作流助手逐步切到新 Intelligence Runtime。

范围：

- Chat 使用新 runtime
- Settings 管理新 Agent、Team、Skill、Knowledge
- 旧 Memory 迁移到 typed knowledge
- `/api/agent` 标记 deprecated
- 最后删除或缩成兼容层

验收：

- 旧能力有新能力覆盖
- 前端不再依赖旧 `src/shared/api/agent.ts`
- 后端旧 Agent 测试迁移完成
- `npm run check` 通过

## 阶段 8：本地模板化与复盘增强

目标：

让本地系统越用越强。

能力：

- 成功工作流自动建议保存模板
- 成功提示词沉淀为 prompt pack
- 成功团队配置保存为 team template
- 按需求推荐历史工作流
- 可选 SQLite
- 可选 embedding 检索

验收：

- 重复任务能推荐历史模板
- 用户能一键复用团队 + 工作流 + 提示词组合
- 知识库能提升规划质量，但不能绕过审批

## 阶段 9：服务器端迁移设计

目标：

本地总验收通过后，再设计 `server-web` 迁移方案。

范围：

- 定义本地 JSON 或 SQLite 知识库导出、导入、回滚方式
- 定义用户、工作区、公共知识的所有权与可见性
- 定义 Agent 调用如何消耗当前用户 provider 或工作区授权额度
- 定义同步冲突、版本、审计和恢复策略
- 将本地 API 映射为服务器安全 API

不做：

- 不直接上线多用户 Agent
- 不直接开放公共知识库贡献

验收：

- 有服务器迁移设计文档或 ADR
- 本地数据能导出为服务器可导入格式
- 所有权、provider 消耗、冲突处理规则可测试

## 阶段 10：server-web 多用户 Agent 开放

目标：

在不破坏本地能力的前提下，让 `server-web` 用户都能使用 Agent。

范围：

- 为 intelligence runs 增加登录用户和工作区归属
- 模型调用走当前用户 provider 配置或被授权的工作区计费策略
- 增加服务器限流、审计 trace、错误治理
- 保持 `desktop` 和 `local-web` 本地行为不退化

验收：

- 两个用户不能互相看到私有 run、知识、provider 配置
- provider 消耗能归因到请求用户或工作区
- 本地验收仍然通过

## 阶段 11：知识库共享、审核和同步

目标：

允许所有用户贡献知识，但只有经过治理后才能成为共享知识。

范围：

- 增加贡献、审核、通过、拒绝、版本管理
- 区分私有知识、工作区知识、公共知识
- 为已审核知识增加同步或导入导出能力
- 保留 source、evidence、owner、reviewer、visibility 元数据

验收：

- 用户贡献知识默认私有或工作区可见
- 公共知识必须审核后才能成为全局指导
- 同步冲突可检测、可处理、可回滚

## 阶段 12：三端同步或服务器中心化扩展

目标：

根据真实使用情况决定做三端双向同步，还是采用服务器中心化共享。

范围：

- 评估 `desktop`、`local-web`、`server-web` 的真实数据流
- 只有产品确实需要时才做三端双向同步
- 如果不需要，保持服务器为共享中心，本地端保留显式导入导出

验收：

- 选型和取舍有文档
- 离线行为、冲突处理、回滚策略通过测试
- 不需要服务器共享的用户仍可完整本地使用
