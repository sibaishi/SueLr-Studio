# Workflow Stabilization Implementation Plan

**Goal:** 基于仓库审计结果，分阶段完成 SueLr Studio 的结构收口、契约统一、状态拆分与工程治理，恢复项目的可持续开发能力。

**Architecture:** 本计划采用“基线治理 -> 后端收口 -> 前端契约统一 -> 状态拆分 -> 质量固化”的顺序推进，避免同时触碰多个高风险面。每个阶段都要求先建立清单与边界，再做迁移与删除，确保现有功能持续可用。

**Tech Stack:** React 19、TypeScript、Vite、Zustand、Express、Node.js ESM、原生 Node test

---

## 执行说明

- 本文档是执行层文档，默认面向对当前仓库不熟悉的工程师
- 每周任务都必须产出“可验证结果”，不能只停留在分析结论
- 每周结束后至少执行一次 `npx tsc --noEmit`、`npm run build`、`npm test`，除非当周任务明确仅处理文档

## 周度节奏总览

### Week 1：仓库基线与文档重建

**当前状态（2026-05-03）**

- 状态：部分完成
- 已完成：文档入口、目录边界、`.gitignore` 与纯净部署范围说明已建立
- 已完成：Week 1 最小 smoke 清单已补齐
- 未完成：首次 Git 提交基线尚未形成
- 收口条件：完成一次 `chore: initialize repository baseline` 类型的基线提交，并使 `git status` 回到可预期状态

**目标**

- 建立可信的 `docs`、Git、运行时目录边界
- 让团队知道哪些目录属于源码，哪些目录属于部署产物或本地数据

**交付物**

- 新版 `docs` 导航、路线图、执行文档
- 仓库目录归属清单
- 运行时目录与发布物清理规则
- 首次仓库基线提交说明

**任务清单**

1. 确认根目录下所有业务目录的用途与归属
2. 复核 `.gitignore` 是否覆盖 `node_modules`、`dist`、日志、运行缓存、存储目录
3. 记录 `storage/`、`workflows/`、日志目录的版本控制策略
4. 明确“可部署纯净版”应保留的目录与文件
5. 重建 `docs/README.md` 作为文档入口
6. 输出总路线图与本执行文档
7. 补齐首次 Git 提交基线说明并完成基线提交

**验收标准**

- 文档可以回答“项目如何启动、哪些目录不能提交、哪些目录属于运行时”
- 后续成员不再依赖旧文档判断当前阶段工作
- 仓库形成可信的首次 Git 基线提交

**风险**

- 如果 Git 根基仍不稳定，后续任何结构优化都会缺乏可回滚基线

### Week 2：后端链路盘点与唯一入口定义

**目标**

- 明确后端哪些模块是当前真实生效实现，哪些是过渡层或旧实现

**交付物**

- 后端实际调用链说明
- 旧 `routes/`、`services/`、`engine/` 与新 `src/modules/` 的职责清单
- 第一版后端收口方案

**任务清单**

1. 列出当前 Express 挂载的所有活跃路由
2. 标记每条路由最终落到的 module / service / engine
3. 标记图片、能力、执行三条核心链路中的跨层调用
4. 识别“只能保留一个”的重复职责模块
5. 决定旧层是迁移、代理，还是封存
6. 输出后端迁移顺序表

**验收标准**

- 开发者能明确知道某类问题应该改哪个目录
- 不再需要通过猜测判断哪个 service 才是真实现

**风险**

- 如果不先画清链路图，后续迁移容易误删仍在使用的旧实现

### Week 3：图片 / 模型能力契约统一

**目标**

- 统一模型能力接入方式，减少不同入口之间的参数漂移和返回格式分叉

**交付物**

- provider 现状对照表
- 统一后的 request / response contract 草案
- image、chat、file 三类能力的参数映射标准

**任务清单**

1. 对比 `src/lib/providers/*` 与 `src/features/workflow/lib/providers/*` 的职责差异
2. 确定唯一保留的 provider 层
3. 列出所有图像请求体构造入口与字段来源
4. 列出所有上游返回解析入口与容错策略
5. 为同步、异步、直接图片、任务态、chat/image 两类接口定义统一结果模型
6. 形成合并或迁移步骤清单

**验收标准**

- 新增模型或改参数时，不需要同时改两套 provider
- 图像相关返回解析有统一入口和回退逻辑

**风险**

- 如果先改业务逻辑再统一 contract，很容易继续累积历史分叉

### Week 4：工作流 store 拆分设计

**目标**

- 把 `workflow` 大 store 从“系统总线”拆回到按职责管理的状态模块

**交付物**

- store 职责拆分图
- 子模块边界定义
- 状态迁移顺序与回归检查点

**任务清单**

1. 列出 store 当前承担的全部职责
2. 识别编辑态、运行态、持久化、导入导出、布局交互等天然边界
3. 定义哪些 action 应转为独立模块
4. 定义哪些 selector 应抽到只读层
5. 设计序列化与恢复逻辑的独立接口
6. 输出最小拆分路径，避免一次性重写

**验收标准**

- store 拆分方案可直接指导代码改造
- 每个子模块有清晰输入、输出、依赖关系

**风险**

- 如果没有先拆职责图，直接动代码会把耦合藏到更多文件里

### Week 5：后端收口实施

**目标**

- 开始把 Week 2 形成的后端链路方案落实到代码层

**交付物**

- 第一批已收敛的后端模块
- 已标注或已封存的旧实现
- 关键链路回归结果

**任务清单**

1. 先从图片模块开始收敛跨层调用
2. 再处理 capabilities 模块对旧服务的直接依赖
3. 为执行链路补充最小必要的分层测试
4. 标记暂未迁移模块的过渡策略
5. 在文档中记录“当前唯一入口”

**验收标准**

- 图片与能力模块的责任边界比当前更清晰
- 回归测试能覆盖迁移后的关键路径

### Week 6：前端 provider 收口实施

**目标**

- 落地 Week 3 的统一 provider 方案

**交付物**

- 唯一 provider 层
- 迁移后的调用清单
- 统一错误与返回模型的落地结果

**任务清单**

1. 确定保留路径与废弃路径
2. 先迁移图像能力调用
3. 再迁移 chat / file / capability 相关调用
4. 合并重复类型定义
5. 删除或封存重复实现
6. 补齐针对返回解析的测试

**验收标准**

- 同类能力只存在一个请求构造入口
- 上游返回格式变化时有统一修正点

### Week 7：工作流 store 拆分实施

**目标**

- 将工作流核心状态拆成可维护模块

**交付物**

- 拆分后的状态结构
- 新旧状态映射层
- 回归用例与行为验证记录

**任务清单**

1. 优先拆出序列化 / 持久化逻辑
2. 再拆执行态与运行恢复逻辑
3. 最后拆布局交互与编辑器 UI 状态
4. 为每次拆分保留最小兼容层
5. 逐步收缩原始大 store 的职责

**验收标准**

- 核心状态逻辑不再集中在一个超大文件
- 单个模块修改不再轻易影响全部工作流行为

### Week 8：质量门禁与长期标准化

**目标**

- 把前几周的结构改造成果沉淀为长期机制

**交付物**

- 工程检查脚本清单
- 契约文档与模块边界文档
- 阶段复盘与下一轮优化建议

**任务清单**

1. 补齐并固化 `type-check`、`build`、`test` 执行规范
2. 视仓库情况补充必要 lint / format 规则
3. 输出 provider contract 与 execution contract 文档
4. 输出运行时目录、部署物、数据目录的长期策略
5. 复盘本轮优化的遗留问题与下一阶段建议

**验收标准**

- 新增功能前，团队已有固定检查动作
- 新人可通过文档快速理解主要结构与边界

## 阶段依赖关系

- Week 1 不完成，Week 2 以后都缺乏可信基线
- Week 2 是 Week 5 的前置条件
- Week 3 是 Week 6 的前置条件
- Week 4 是 Week 7 的前置条件
- Week 5、6、7 至少每周只允许一个“主风险面”为高强度改造对象

## 执行策略

### 策略 A：稳态推进

- 适合当前仓库
- 每周只聚焦一个主问题面
- 优先保证可运行、可回滚、可验证

### 策略 B：并行重构

- 不推荐当前采用
- 除非团队已补齐完整测试与清晰模块边界，否则会明显放大回归风险

**推荐选择：策略 A**

原因：

- 当前仓库的主要问题是边界不清，而不是纯实现速度不足
- 先收口再提速，比并行大改更稳

## 每周固定检查清单

- 本周目标是否只针对一个主问题面
- 本周是否明确了要保留、迁移、删除的对象
- 本周是否记录了新增或变更的唯一入口
- 本周是否更新了 `docs` 中对应说明
- 本周是否完成至少一次验证命令执行

## 阶段完成定义

- **完成**：已有代码 / 文档 / 测试 / 说明的可验证结果
- **部分完成**：分析完成，但迁移或验证未闭环
- **未完成**：仅有口头结论，尚无文档或执行产物

## 建议的任务分派方式

- 负责人：掌控阶段边界、验收标准、回归门槛
- 前端执行者：优先负责 provider 收口与 store 拆分
- 后端执行者：优先负责执行链、图片链路、能力模块收口
- 文档维护者：负责每阶段同步更新路线图与执行计划状态

## 首轮建议从哪里开始

如果现在立刻进入执行，建议先做三件事：

1. 固化 Git 基线与运行时目录规则
2. 画出后端真实调用链
3. 画出前端 provider 重复关系图

这三件事完成后，后续优化会从“凭感觉修”变成“按边界推进”。
