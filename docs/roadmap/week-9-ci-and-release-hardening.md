# Week 9 CI And Release Hardening

## 1. 本周目标

Week 9 的目标不是继续拆业务结构，而是把当前已经完成的 Week 1-8 治理成果固化成团队日常可复用的工程基线。  
这一周要解决的是“本地已经更稳了，但提交、环境、发布、回滚仍然靠人记住流程”的问题。

本周完成后，项目至少应具备以下能力：

1. 任意一次 push 或 PR 都会自动跑最小质量门禁
2. Node 版本、环境变量和启动前置条件有唯一可信说明
3. 发布和回滚不再依赖口头经验
4. 新同事可以依靠文档独立拉起项目并完成最小验收

## 2. 落地内容

### 2.1 建立 CI 最小门禁

新增或补齐一条项目级流水线，至少覆盖：

- `npm install`
- `npm run check`

触发范围建议为：

- push 到主分支
- pull request

目标不是一次把所有自动化都塞进 CI，而是先把当前已有的结构门禁、类型检查、构建验证和后端测试稳定接入。

### 2.2 锁定运行环境基线

补齐并统一以下基线信息：

- Node 版本声明
- 包管理与安装方式说明
- `.env.example`
- 前后端启动顺序
- 本地开发常见问题说明

重点是让“环境不一致导致的误判”从日常问题里消失。

### 2.3 收口发布与回滚说明

新增或完善部署文档，至少覆盖：

- 构建产物说明
- 前后端部署步骤
- 必填配置项
- 首次部署检查项
- 发布后验收项
- 回滚操作步骤

Week 9 不要求引入复杂发布平台，但要求先把“怎么稳定上线”和“出问题怎么退回去”写成可执行说明。

### 2.4 补齐基线级人工冒烟入口

在自动验证之外，为发布前保留一组最小人工确认项，例如：

- 前端可打开工作流页面
- 后端接口可正常启动
- 设置页能正确读取与保存配置
- 一条最小工作流能够运行

这组冒烟项的职责不是替代自动化，而是给发布动作保留最后一道现实校验。

## 3. 验收结果

当前已落地：

- 已新增远程 CI：`.github/workflows/ci.yml`
- 已统一 Node 基线：`.nvmrc`、根 `package.json`、`backend/package.json`
- 已补齐运维文档：
  - `docs/ops/environment-baseline.md`
  - `docs/ops/deployment-and-rollback.md`

Week 9 完成后，应至少确认：

- CI 已经能够在远程环境自动执行 `npm run check`
- 项目运行环境基线有单一入口文档
- 发布和回滚步骤有明确文档承接
- 新人或非作者本人可以按文档完成本地拉起

## 4. 对后续周次的直接输入

Week 9 的成果会直接服务 Week 10-12：

1. Week 10 的前端 E2E 会优先接入已经存在的 CI
2. Week 11 的 store 纯逻辑测试会直接复用统一门禁入口
3. Week 12 的发布纪律、回归矩阵和观测说明，会建立在 Week 9 的发布文档之上

换句话说，Week 9 是后面三周自动化和发布工程化的基座。
