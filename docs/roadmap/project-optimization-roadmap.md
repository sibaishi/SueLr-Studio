# SueLr Studio 优化路线图

## 1. 背景

本路线图基于 2026-05-03 的仓库审计报告整理，目标不是继续堆功能，而是先把项目拉回到“可持续开发”的状态。

当前项目的主要问题不是单点 bug，而是三个层面的系统性负担：

- 仓库基线不稳定，版本追踪与发布物边界不清晰。
- 后端处于新旧架构并存状态，真实执行链路不够单一。
- 前端状态管理与 provider 抽象过于集中且重复，扩展成本持续升高。

## 2. 优化目标

### 2.1 业务目标

- 保持现有工作流编辑与执行能力可用。
- 降低新增模型、节点、图片链路改动的回归风险。
- 为后续功能开发建立可靠基线，而不是在脆弱结构上继续叠加复杂度。

### 2.2 工程目标

- 建立清晰、可提交、可回滚的仓库基线。
- 将后端请求入口、执行流程、服务层责任收敛为单一事实源。
- 将前端 provider、API 映射、workflow store 拆成可维护模块。
- 为后续集成、部署和质量门禁补齐文档与验证流程。

## 3. 优先级矩阵

### P0：必须立即处理

- Git 基线与运行时目录边界。
- 后端新旧架构混用。
- 前端 provider 双实现分叉。

### P1：必须在下一阶段处理

- 工作流大 store 拆分。
- 统一 API contract 与返回 envelope。
- 文档编码与 Windows 环境可读性校验。

### P2：随结构修复同步推进

- 质量门禁脚本补齐。
- 执行链路测试加密。
- 构建产物与部署策略梳理。

### P3：中长期优化

- 运行日志、存储、工作流数据的部署抽象。
- 多环境配置与远端存储预留。
- 面向未来集成的契约文档与模块边界标准化。

## 4. 目标状态

项目在完成本轮优化后，应达到以下状态：

- `git status` 在常规开发下保持干净或可预期。
- 后端只保留一条明确的生效链路，开发者不需要猜“该改哪个目录”。
- 前端所有模型能力接入只走一套 provider contract。
- workflow store 不再承载所有职责，执行态、编辑态、持久化逻辑可分别测试。
- 文档能够直接指导新同事完成启动、定位、修改与验证。

## 5. 分阶段路线

### 阶段 1：基线治理

目标：先让仓库和交付边界可信。

交付结果：

- 清晰的 `docs` 结构与执行计划。
- 仓库提交基线、忽略规则、运行时目录策略明确。
- 发布物、日志、存储目录的归属规则形成文档。

### 阶段 2：后端链路收口

目标：明确后端唯一生效架构。

交付结果：

- 梳理 `route -> module -> service -> engine` 的实际调用图。
- 标注旧 `services/` 与新 `src/modules/` 的保留/迁移/封存策略。
- 收敛图片、能力、执行链路中的跨层依赖。

### 阶段 3：前端契约统一

目标：把“能力接入”从工作流实现中剥离出来。

交付结果：

- 统一 provider 层。
- 统一 API request/response 类型与错误模型。
- 明确 chat、image、file 等不同能力的入参与出参标准。

### 阶段 4：状态管理拆分

目标：降低工作流编辑器的维护压力。

交付结果：

- 大 store 按职责拆分。
- 选择器、动作、序列化、运行态恢复解耦。
- 关键状态逻辑具备更细粒度测试入口。

### 阶段 5：质量与长期演进

目标：把结构优化沉淀成长期可复用的工程机制。

交付结果：

- 增加 type-check、test、build、必要 lint 的质量门禁。
- 形成执行链路、provider 契约、存储边界的长期文档。
- 为未来接入更多模型、部署方式和集成场景预留标准化接口。

## 6. 里程碑与验收

### M1：仓库基线可信

验收标准：

- 运行时目录不会混入发布或版本基线。
- 文档能说明如何启动、构建、测试、清理运行产物。

### M2：后端链路唯一

验收标准：

- 关键模块不再依赖“表面新、实则旧”的混合调用。
- 图片、能力、执行三条主链路有清晰归属。

### M3：前端接入层唯一

验收标准：

- provider 不再重复实现。
- 关键类型定义有唯一来源。

### M4：工作流状态可拆可测

验收标准：

- `store.ts` 不再是单点超大核心。
- 核心状态逻辑可按模块验证。

### M5：持续迭代机制建立

验收标准：

- 每次新增能力有固定接入位置、固定测试方式、固定文档更新点。

## 7. 风险与应对

### 风险 1：优化中断现有功能

应对：

- 每阶段都以“先梳理、后迁移、最后删除旧实现”为原则。
- 以现有通过的 `type-check`、`build`、`test` 作为最低回归门槛。

### 风险 2：文档与代码再次脱节

应对：

- 每个阶段结束都要求同步更新执行文档状态。
- 所有新入口、新契约必须在对应文档中登记。

### 风险 3：团队继续绕过新结构改旧代码

应对：

- 在执行文档中明确“唯一生效层”。
- 旧层在过渡期内标注用途，迁移完成后及时封存或删除。

## 8. 建议执行原则

- 先稳基线，再动结构，再做体验。
- 每次只收一个口，不做大而全重写。
- 不同时改执行链、provider、store 三个高风险面。
- 所有阶段都要有可验证产物，而不是只写“完成重构”。
